| ad_closed | P0 / 新增 | 插屏关闭确认一次；不产生complete/cancel/reward事件。激励沿用complete/cancel终态 | request_key、close_status |
| ad_reward_pending | P0 / 新增 | 完整观看已确认但奖励尚未持久化成功时；每claim状态变化一次 | claim_key、reward_type、reason；发现“看完没到账” |
| ad_reward_granted | P0 / 已有需补幂等 | 奖励成功兑付且持久化确认后，每claim一次；重启恢复归并原claim，不能二次记奖励 | claim_key、request_key、reward_type、reward_qty、grant_source=normal/recovery |
| ad_reward_failed | P0 / 新增 | 奖励无法兑付或需人工处理时；临时存储失败仍保留pending，不伪装最终丢奖 | claim_key、reason、recoverable |
| solo_start / solo_complete | P0 / 已有需补关联 | 开局、最终结算按round_key；复活沿用同局，不能记成新开局。若当前solo_complete包含可复活失败，新增is_final_result区分，统计只取最终态 | round_key、level、content_revision、result、revive_count、remaining_goal_bucket |
| gameplay_resumed | P0 / 新增 | 广告关闭/领奖后第一次有效棋盘操作或新局开始，按request一次 | request_key、round_key、resume_kind；前台可操作60秒内标及时续玩 |
| item_used | P1 / 新增或复用核对 | 道具实际生效并扣库存后一次，不在点击选择时记 | round_key、item_type；库存混合时不强行宣称是某次广告奖励被使用 |

已有shop_ad_reward_success/failure/limit可保留诊断，但不与ad_reward_granted相加。当前ad.js的finish对插屏关闭也会发ad_complete，实施时必须按format拆分并升级schema；历史数据不能直接混用。当前ad_request可能早于忙碌拦截，也可能有缺终态路径，需补block/unknown分类，而不是强行让所有计数单调递减。

## 三、字段与关联

| 类别 | 字段建议 | 约束 |
| --- | --- | --- |
| 公共 | schema_version、event_time、received_at、app_version、content_revision、environment、platform | event_time用UTC时间戳，报表按Asia/Shanghai；测试/开发/模拟流量明确标记并排除 |
| 点位 | placement、entry、format、item_type、reward_type、reward_qty | 有限枚举；本地道具key应与ITEM_DEFS逐一映射，不凭中文名猜代码值 |
| 玩法 | mode、level、round_key、result、moves_left_bucket、remaining_goal_bucket、revive_count、heart_before_bucket | 只取必要低敏标量，目标进度不等于通关概率；不上传棋盘/存档全文 |
| 过程 | opportunity_key、action_key、request_key、claim_key、stage、reason、latency_bucket | 过程键仅用于一次业务实例去重；不复用身份、登录token或设备ID |
| 获客 | cohort_date、channel、campaign_key、creative_key、os、attribution_version、traffic_type | 仅从有权限且可验证的平台归因/汇总来源取得；入口scene不等于付费归因 |

当前analytics.js白名单不接受上述全部新字段，且拦截session/user/id类字段；这是一份拟议数据合同，不能只开REPORTING_CONFIG就当已实现。过程键、跨日去重与分群能力需要单独评估最小化采集、存储周期、用户删除和隐私声明，未批准前不绕过过滤器。

新增用户、DAU、跨日留存优先使用平台有权限的去重汇总。当前匿名本地事件不能天然计算跨设备/重装后的新增或UV。若平台没有可用分群连接键，方案第一阶段只做平台支持粒度的ROI和匿名点位次数漏斗；UV、用户LTV分群明确记不可用，不以请求数替代人数。未经批准不新增持久身份跟踪。

去重与时序：事件event_key由业务键＋事件类型＋允许的状态序号生成；网络重传保留同键。观看终态与奖励状态分两条状态机，complete可以随后pending再granted。迟到回调不能修改已结束请求的奖励；迟到上报可以校正原统计日期，保留接收时间。超时请求记unknown/failed但不补发奖励。收益以平台最终计费为准。

## 四、点位漏斗指标

工作簿“点位漏斗”每行是“机会发生日×固定分析人群×placement×entry×道具”。所有后续事件回挂到该机会，不拿当天不同请求阶段的总数硬除。实时看板仅作未完结观察；正式日表在请求、奖励恢复和续玩观察均核对后标“已核对”，后续迟到数据可修订。

| 指标 | 分子 / 分母 | 解释 |
| --- | --- | --- |
| 入口点击覆盖率 | 至少点击一次的可见机会数 / 可见机会数 | 多次点击同机会去重；不是按钮点击总次数/曝光帧数 |
| 展示成功率 | 去重show请求数 / 去重逻辑request数 | 包含被适配器拦截的请求；结合blocked/load诊断，不称填充率 |
| 完整观看率 | 已确认show且complete的request数 / 已确认show的request数 | complete但缺show的异常单列，不伪造展示 |
| 兑付率 | 上述complete请求中最终到账的claim数 / 上述complete请求数 | 一个request对应一个claim；恢复发奖不重复 |
| 领奖后及时续玩率 | 上述到账请求中60秒前台可操作时间内续玩数 / 上述到账请求数 | 广告原生覆盖及后台时间不计；超时未续玩是未续玩，不推断卸载 |
| 插屏关闭率 / 及时开局率 | 同时确认show和关闭的请求数/展示数；这些关闭请求后60秒前台可操作时间内开局数/这些关闭请求数 | 插屏没有入口点击、完播、奖励指标；返回首页仍有后续观察窗口 |
| 广告渗透率（扩展） | 当日完成激励的去重用户 / 同人群当日活跃用户 | 另列单人开局用户分母版本，名称明确；跨点位UV不可相加 |
| IPU（扩展） | 平台有效展示 / 同人群活跃用户；新用户版本另用买量新增分母 | 激励/插屏拆开；不能以观看用户作为全量分母 |

工作簿N列关联取消、Y列插屏关闭均只填与确认show关联的请求集合，Q列插屏及时开局进一步限定在Y列集合内。complete/cancel/closed存在但show缺失的终态均另列异常清单，不填入这些交集列，也不丢弃原事件；原始终态数量可能高于交集数量。

工作簿先计算可靠的次数漏斗；UV/留存在后续取得合法去重汇总后补入，避免模板输出虚假的人数指标。点位收益只有在平台确实提供对应广告单元/点位粒度时才能直接归属；当前多个激励点位共享广告单元，不能默认平台收益能拆到placement。均价分摊仅可另标“估算”，不进入真实ROI主表。

## 五、ROI回收合同与工作簿

### 时间与人群

- 首版仅统计paid_new（付费获客新增），不混自然/社交新增、回流、测试、重复激活。获客成本必须含同批所有可归因新增，包括没有开始单人或没有看广告者。
- cohort_key对应互斥的获客日期×渠道×计划×素材×系统×归因版本。平台不支持素材收益归因时降到双方都有的粒度，不把总收入摊给素材后叫实测。
- 项目内部D0=获客自然日；D1累计0–1日，D7累计0–7日，D14累计0–14日，D30累计0–30日，均按北京时间。D7含8个自然日。平台“7日ROI”可能用7×24小时或7个自然日，不能直接填进项目D7列；优先用日级数据重算，无法转换则另表保留平台原口径。
- 数据完整截至日指买量和收益均已完整且可核对的最后一个自然日，不是下载时间或今天。仅当截至日≥cohort_date＋窗口日龄且该行“已核对”才进入汇总。汇总按各窗口成熟样本分别计算，窗口之间可能不是同一批cohort，不能把它画成同一批玩家的LTV曲线；对比曲线需筛同一组已成熟D30的cohort。

### 数据来源与职责

| 输入 | 取数口径 | 无数据时 |
| --- | --- | --- |
| 媒体消耗 | 投放平台按获客cohort归属的实际消耗，含本期实际抵扣广告金的价值 | 不拿充值额替代消耗 |
| 已消耗广告金 | 本期实际抵扣且可对账金额，不是已发放/待解锁额度 | 已确认无则填0，未知留空 |
| 新增人数 | 同归因cohort唯一新增用户数，去除测试/重复激活 | 无法唯一归因则不算CAC和cohort回收 |
| 激励/插屏净收入 | 同批用户、固定窗口内开发者可得收入，已扣平台分成/无效流量调整 | 不重复扣分成；未知留空，确认0才填0 |
| 可变成本 | 同cohort同窗口可归属的服务/发行等成本；定义与分摊方法一致 | 不能默认为0；固定研发成本不混入 |
| 来源凭据 | 原始报表文件/导出批次、时间、归因版本与核对人记录 | 只有事件次数不构成收益凭据 |

| 工作簿指标 | 公式 | 解释 |
| --- | --- | --- |
| 净广告收入 | 激励净收入＋插屏净收入 | 不含未兑现政策补贴 |
| CAC | 媒体消耗/付费新增 | 消耗含广告金价值，另算现金口径 |
| 媒体回收率（ROAS） | 净广告收入/媒体消耗 | 行业常称ROI；100%只覆盖媒体消耗 |
| 现金投放回收率 | 净广告收入/(媒体消耗－已消耗广告金) | 是现金消耗归属口径，不等于银行现金到账；分母0显示不适用 |
| 贡献金额 | 净广告收入－媒体消耗－可变成本 | 不扣固定研发/总部成本，不叫净利润 |
| LTV_N | 固定窗口净广告收入/原始新增人数 | 未扣获客；未成熟不得外推成终身LTV |
| 首个观察到的覆盖窗口（人工判读） | 筛选同一cohort的成熟合格行，按日龄升序找到首个媒体回收率≥100%的窗口；工作簿不自动输出最早窗口 | 只能说“截至D14已覆盖”，不能声称第14天回本；精确天数需要逐日累计表 |

主表每行cohort×窗口；同一cohort不同窗口会重复消耗和人数。禁止跨窗口直接加总；汇总只加同窗口合格行后相除，不平均各行百分比。同键同窗口重复的两行均排除并提示；空值不当0，未成熟不算0回收。素材/渠道横向比较同时控制观察成熟度、投放时段和流量组成。

## 六、验收与上线前准备

本轮交付不接平台。实施时先确认分析服务、权限、费用、身份/去重方案与隐私范围，再由现有负责人映射事件和接数据。平台官方接口与账户能力届时复核，本方案不承诺支持用户级收益回传或特定SDK接口。

最小核对案例：五placement和各entry；确认框取消不计视频取消；完整/提前关/无填充/加载失败；广告后台/超时/迟到重复回调；存储失败后恢复到账一次；插屏无reward且关闭不计complete；重绘不增曝光；跨日奖励归原机会、收益仍按平台归因窗口；模拟和开发流量排除；缺show终态单独可见。

表格核对：空输入不输出收益0；明确0收入得到0回收；截至日未成熟不能参与；重复键阻止双算；两个cohort按消耗加权；广告金0与空白不同；全额广告金时现金分母0；D0、D1、D7、D14、D30边界正确；输入数据更新后公式随之改变。未经真实导出对账不能宣称线上ROI已可观测。

建议批准实施顺序：先P0闭环与五点位/入口区分，再打通平台支持粒度的获客和收益汇总，最后补UV/留存及更细粒度分析。首批决策看“复活次数分组的最终通关和续玩”“局内道具领后使用”“补心后开局”“插屏后开局及留存”。观察相关性不等于广告造成流失；涉及改奖励/频率/难度的验证另定实验和产品门槛。

## 七、依据与当前边界

项目事实依据：`match3-wechat/js/core/ad.js`、`analytics.js`、`config.js`、`ad-rewards.js`、`main.js`以及[广告启用草案](ad-activation-draft.md)。2026-10-18核对广告开启、mock关闭、远程上报关闭；analytics事件本地200条/7天。交付时另有会话并行增加本地广告诊断及阶段/错误分类，相关改动由其负责人维护；本方案中的“新增”指拟议商业测量事件，不否认诊断已能记录类似阶段，也不把诊断视为线上汇总能力。实施前逐项复核并复用这些现有能力。无本项目真实投放和收益导出，模板不填写外部行业数据或虚构实测。前轮公开ROI案例仅说明为什么需要成熟cohort，不作为本项目回收目标。

# 猫咪陪伴成长 v1 · 产品草案

更新：2026-09-25。四猫20阶段静态原画已接受并接入，原画子包1.0.3开发候选已上传。新增20篇阶段小故事与首页陪伴已完成本地实现；2026-09-26用户批准五项优化（含紧凑切换弹窗），当前已接入阶段一致、固定章节、成长跳转和可领/未读提示，等待最终运行验收，未上传该功能。陪伴展示只记住本机外观快照；真实领养/成长云进度和第三/四只解锁规则仍未完成。动画延期至下版本。当前证据、平台未验项与下一步统一维护于 `project-status/development-steps.md`。

已确认视觉基准：`assets/_incoming/cat-catalog-v1/catalog-concept-v8-round-calico.png`。用户明确“可以，就按这版吧”。沿用四猫形象、2×2图鉴卡片、月夜花园和状态层级；布丁采用圆润脸颊、柔和下巴、轻微歪头、自然错位前爪的正面趴卧形象。后续角色资产与成长阶段保持身份一致，未经新的用户修改要求不重新设计已接受方向。v1至v7仅为修订历史。

## 已确认的范围

- 首页先进入猫咪图鉴，领养与成长均从图鉴进入；先规划图鉴，再展开成长页面。用户指出图鉴是入口并要求继续此方向。
- 成长体现「初见到亲密」的关系变化，保持猫咪身份和外形特征；不采用幼猫长成成年猫的路线。
- 首期 4 只猫，每只 5 个成长阶段，每阶段 1 张专属原画，共 20 张。用户已确认从原2只扩展至4只，原10张规模不再适用。
- 原画通过姿态、表情和场景变化体现亲密程度，阶段与原画一一对应。
- 用户要求不同猫咪的形象参考真实不同品种，不能只换毛色；需从脸型、耳形、五官、毛长、体型和尾巴做明显区分。当前四猫外观以已接受v8为准。
- 核心循环：玩游戏获得小鱼干 → 玩家亲手点击喂猫 → 提升该猫亲密度 → 解锁阶段原画。对局结束不直接增加亲密度。
- 领养方式：首次任选一只免费领养；第二只在累计游玩 7 天后免费解锁，不要求连续。每个活跃日完成至少 1 局有效对局，同一天不重复累计；具体有效对局校验口径随完整 PRD 确定。
- 第二只猫的解锁按累计活跃日计算，与喂养进度分开，不消耗小鱼干、不要求第一只满级。
- 产品方向优先低持续维护的留存内容。用户认为周末主题关卡需要持续更新、维护量较大。

确认来源：当前产品讨论中用户选择亲密关系成长，最终明确认可「4 只猫 × 5 张原画，共20张」，确认通过游戏获取小鱼干后亲手喂猫，并接受第二只按累计游玩 7 天的方式解锁；随后明确图鉴应作为领养、成长的入口。本轮另以“确认”接受首只猫成长样板的数值与实现范围，随后用户要求先补齐全部原画；资产出图已执行，真实服务仍未进入执行。

## 成长样板采用方案（用户已确认）

目标用户与平台沿用项目：偏好治愈猫咪主题的微信小游戏玩家，原生 JavaScript + Canvas。目标是让现有对局产生可感知的陪伴积累，提高回访与持续游玩意愿。

- 仅一种食物、每日有限获取，不引入饥饿或离线衰退。
- 阶段：初见、熟悉、信任、依恋、挚友。每天2份均喂同一只时，对应0、2、5、10、21个活跃日；这是资源换算，不是固定实际历时。
- 旧原画永久保留并允许自由切换；奖励以展示和互动为主，不增加对战属性或金币倍率。
- 同一套原画复用于图鉴和成长详情；首页只新增「猫咪图鉴」辅助入口，不并列增加领养/成长入口，遵守好友对战优先的层级。
- 建议首期不含家具装修、繁殖、装备、限时主题关卡及新的广告入口。

### 资源与成长节奏

- 每天完成第 1 局和累计第 3 局有效对局，各获得 1 份小鱼干，每账号每天共 2 份；单人、每日挑战、好友对战共享计数与上限，不能按猫咪或模式重复领取。
- 建议正常完成结算的胜局、败局均可计入，主动退出不计；具体有效对局与异常恢复口径须结合现有结算可信度确认，不能仅信任客户端计数。
- 小鱼干进入共用库存，可储存且不跨日清空。每次手动喂食消耗 1 份，给当前选中的猫增加 1 点亲密度；喂食前明确显示猫咪与消耗。
- 五阶段累计亲密度 0 / 4 / 10 / 20 / 42。每日获得 2 份并全部喂给同一只猫时，约需 0 / 2 / 5 / 10 / 21 个活跃日；分养两只会延长单只成长时间，预存资源可加速后来获得的猫，不能宣称每只猫固定需要 21 个自然日。
- 建议切换猫咪保留各自进度；满级猫保留免费互动，停止消耗食物，不自动将喂食转给另一只猫。四只均满级后不增加新的强制日常。
- 暂不使用金币购买或广告兑换小鱼干，避免首期增加额外经济与商业化规则。

## 已确认的四猫概念形象（以v8为准）

| 芝麻 | 海豹重点色暹罗，楔形脸、大三角耳、蓝色杏仁眼、修长短毛身形与细尾 | 机灵活泼，从试探伸爪到翻肚皮玩耍 |

## 首只猫成长样板实现范围（历史，用户明确“确认”）

用户明确确认以下成长详情 develop-only 可点击样板规则；本轮不接入正式经济或云端：

- 五阶段名称固定为「初见、熟悉、信任、依恋、挚友」，亲密度阈值为 `0 / 4 / 10 / 20 / 42`。
- 每次手动喂食消耗 1 份小鱼干并增加 1 点当前猫亲密度；不设置饥饿、衰减或对战属性。
- 每日最多获得 2 份小鱼干：当天第 1 局和累计第 3 局有效完成各 1 份；单人、每日挑战、好友对战共享上限，主动退出不计。
- 解锁后的成长原画永久可回顾；满级保留互动入口但不再消耗小鱼干。
- 第三、第四只猫的解锁条件继续留空；本阶段只演示首只猫的五阶段成长，避免假定未定规则。

本轮只实现本地内存样板：已领养详情 → 喂食确认 → 亲密度/阶段更新 → 新阶段解锁提示 → 原画回顾；不接云端、不改真实钱包、不批量生成20张原画。第一张沿用接受图，其余阶段显示明确的“原画待制作”面板，可验证开放/锁定与展示阶段选择，不假称新增原画完成。浏览器工具栏模拟完成局、主动退出、下一日以验证每日1/3局产出；真实游戏不会在本轮发鱼。云端持久化和完整原画生产另设门槛。

## 页面与状态草案

| 页面或区域 | 内容与动作 | 需要覆盖的状态 |
| --- | --- | --- |
| 首页辅助入口 | 「猫咪图鉴」进入图鉴；返回时恢复首页 | 正常、第二只可领养提示 |
| 图鉴主页面 | 四张猫咪收藏卡、已领养数量、小鱼干库存；点击卡片进入对应详情，返回首页 | 首次选择、已领养/未解锁混合、达标可领养、四只已领养、满级、加载/失败 |
| 猫咪详情·领养状态 | 第一阶段原画、性格简介与领养条件；首次可免费领养任一只，第二只不足7天时查看累计进度，其余按各自待定条件展示，满足后免费领养；返回图鉴 | 首次可选、未解锁、达标可领养、提交中、失败可重试、领养成功转成长详情 |
| 猫咪详情·成长状态 | 当前阶段原画、五阶段轨迹、下一奖励与小鱼干库存；手动喂当前详情中的猫，返回图鉴 | 正常、资源不足、提交中、失败可恢复、满级 |
| 阶段解锁弹窗 | 展示新原画与奖励，确认后返回详情 | 首次解锁、重复回包不重复发奖 |
| 原画回顾 | 从详情中的阶段节点预览已解锁原画、选择该猫的展示形象，关闭后返回详情 | 已解锁可查看、未解锁仅显示阶段奖励提示 |

### 导航与交互约定建议

- 主链路：首页 → 猫咪图鉴 → 选中猫咪详情 → 领养或喂食。无需独立领养大厅、成长大厅或额外收集册。
- 点卡片只打开详情，不立即领养或消耗食物。详情主按钮随状态切换为「免费领养」「去玩一局」「喂食 · 1份小鱼干」或满级免费互动，锁定条件始终可读。
- 喂食目标始终是当前详情展示的猫，避免另一个隐藏的陪伴猫选择导致误喂。提交时防止重复操作，失败不显示已成功，重试不得重复扣除或发放。
- 第一只领养成功后立即切换至该猫成长详情；返回图鉴时第一张归为已拥有，其余卡片显示各自解锁条件与进度。第二只解锁和第二只已领养必须明确区分。
- 小鱼干不足时提供获取规则和返回现有玩法的入口；满级时停止消耗食物，已解锁原画仍可回顾。
- 活跃日统计建议从首次领养当日开始、当日有有效对局即可计入，以北京时间自然日区分，不追溯历史签到。此起点及有效对局口径待完整 PRD 确认。
- 云端加载或读取失败时保留明确的加载/重试状态，不能把读取失败显示成未领养或清零。离线查看能力与正式存储方案一起确定。

### 图鉴主页面视觉简报

- 沿用「月夜猫咪花园」：雾蓝与淡紫背景、珍珠质感卡框、粉色点缀、深靛蓝可读文字。优先让猫咪原画成为视觉中心。
- 用户已接受顶部不放标题，返回、已领养数量与小鱼干同行；内容上移40px。原画等比例展示，不为塞入卡片压缩宽高比。
- 首期四只猫，建议使用2列×2行的收藏卡，每张保留大幅猫咪画面，不铺大量空槽，也不放无计划的「敬请期待」。短屏允许内容滚动，返回和安全区不受影响。
- 每张卡包含原画、名字、状态和清晰入口。已领养卡显示当前阶段与五个阶段标记；未领养卡展示第一阶段原画与对应解锁条件；第二只显示「累计陪伴 X/7 天」，不把整张猫咪涂黑。未解锁的后续四张原画保留发现感。
- 四张卡和详情复用原画，不额外计入新猫咪插画。动态文案、进度、按钮与命中区由 Canvas 绘制，概念图不充当正式交互界面。
- 首个视觉交付以「一只已领养、一只可领养、两只未解锁」为代表状态，检查同屏信息层级；其余状态在同一版式下扩展。先确认这页，再展开成长详情。
- 用户已接受v8概念，文件见本文顶部；原v1不再是采用基准。已从接受稿提取四块插画，用于可运行样板；并非制作完20张独立成长原画。20张原画的分辨率、加载与包体方案必须在生产前核对现有预算，不能默认全部塞入主包。

验收重点：玩家能从图鉴识别拥有状态、第二只的解锁条件、当前成长阶段，并明确知道点击后去哪；可领养、可喂食和满级不能混淆。页面具体视觉与完整状态仍待用户审阅。

## 建议推进顺序，待用户确认

1. 确认图鉴优先的页面清单与本顺序，集中评审资源数值和活跃日统计口径，补齐 PRD。
2. 先做图鉴主页面概念：确认四只猫的基础形象、卡片层级、领养与成长入口。到实际生成时明确工具、类别、数量/限额与授权；先做一个代表状态，不批量生成20张。
3. 用最少必要素材实现图鉴可运行样板，覆盖首次选择、未解锁、可领养与已领养状态，检查窄屏和安全区，并进行独立QA与用户视觉验收。样板临时数据须明示，不计为真实领养。
4. 在已接受图鉴基础上展开猫咪详情、手动喂食、五阶段与原画回顾，再按批准范围生产完整原画；先验证单只猫的身份一致性。
5. 接入真实领养、活跃日、食物与亲密度存储；验证重复请求、恢复、跨日和原有玩法。独立验收后，具体部署/发布另按就绪动作获取授权。

详细责任、输入和阶段验收见 `project-status/development-steps.md` 的猫咪图鉴增量草案。图鉴优先不代表成长功能被取消，后续仍需完成已选的整体功能。

效果评估建议关注首次成长交互完成率、第 7/14 天回访、阶段到达率和第二只猫的培养率；先建立基线，不预设未经验证的提升幅度。
